# User Decisions and Technical Discovery

This is the shared policy for Isaac skills. Apply it where decisions or
evidence gaps affect the current task.

## Technical Facts: Agent Discovery

Unknown file paths, runtime IDs, callback owners, signatures, source versions,
registration and test commands are **Unverified — discovery required**, not
user design choices. Search the actual project and matching authoritative API
evidence. Continue authorized independent work. If evidence cannot be accessed,
state the precise limit; ask for missing access/information only when needed.
Do not make the user choose API facts or request permission for routine research.

A fact established from source may still lack runtime proof. Record that boundary
rather than converting it into a user decision. Existing incorrect code does not
override documented/matching implementation semantics.

## Active TBD: Only a User Choice

Use **TBD — user decision required** for genuinely unresolved mechanic, balance,
art, route, dependency policy or persistence semantics that affect this turn.
First check the conversation, approved project decisions and any explicit
delegation. An omitted field in the latest message is not automatically a new
choice. Ask a concise question only if a genuine unresolved user-owned choice
affects the next dependent action; explain its consequence once. No mandatory
heading, final section or repeated decision list is required. Stop only the
mutations that would choose that unresolved alternative, and continue authorized
independent work.

Carry forward explicit design choices and applicable standing preferences as
design inputs. Reuse authorization when the same action was already authorized.
A standing requirement for new mods applies to new mods; preserve a different
explicit policy in an existing project until migration is requested. Routine module naming, file placement and callback selection can
be resolved from evidence within the authorized task.

## Execution And Reporting

Routing selects the skills needed for the task. Continue authorized implementation,
debugging, review or verification after selection; do not request approval for
the route or ask again whether to perform already-requested work. A request for
only a plan, analysis or route remains limited to that deliverable.

Across Isaac skills, contract fields, handoff templates and completion checklists
are references for the applicable technical work, not mandatory response schemas.
Check the affected callback, ownership, state, RNG, persistence, dependency and
verification contracts; do not drop an applicable invariant to shorten output.
Reuse adequate existing tests and only add coverage for changes or real gaps.

Present the outcome, relevant changes and evidence, material verification limits,
and any genuinely pending decision in one coherent response. Merge overlapping
skill checklists, omit irrelevant fields, and do not repeat confirmed decisions
or require a particular heading, table or field order. For a handoff, retain the
facts another implementer needs. Use a fixed schema only when the user, an actual
consumer/tool format or the specific deliverable requires it. Static checks and
source review must still be distinguished from in-game validation.

## Examples

Unknown callback signature: research the matching release source, not "user
decision required: choose callback parameters".

User has already chosen +1 damage and REPENTOGON required: preserve both; inspect
native formula stages and remove duplicate contribution without reopening either.

Unspecified behavior when no legal gallery room exists: a real design choice if
no existing policy or delegation settles it. Explain the consequence, continue
testing room eligibility, and do not silently substitute another mechanic.
