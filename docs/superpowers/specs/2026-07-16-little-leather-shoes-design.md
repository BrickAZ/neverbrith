# 小皮鞋与流量系统设计

日期：2026-07-16  
目标环境：普通 Repentance，不以 Repentance+ 为开发或运行前提。

## 1. 范围与锁定配置

本功能增加一个常规被动道具和三个隐藏的一次性衍生收藏品：

| 本地 ID | 中文名 | 英文名 | 品质 | 进入常规池 |
| --- | --- | --- | --- | --- |
| 32 | 小皮鞋 | Little Leather Shoes | 2 | 是 |
| 33 | 流量：开箱 | Traffic: Unboxing | 0 | 否 |
| 34 | 流量：曝光 | Traffic: Exposure | 0 | 否 |
| 35 | 流量：热度 | Traffic: Heat | 0 | 否 |

小皮鞋使用 `offensive summonable` 标签。它进入以下道具池：

- 宝箱房池：`Weight=1`、`DecreaseBy=1`、`RemoveOn=1`；
- 商店池：`Weight=1`、`DecreaseBy=1`、`RemoveOn=1`；
- 恶魔房池：`Weight=0.1`、`DecreaseBy=1`、`RemoveOn=1`。

三个流量衍生道具使用隐藏注册，不进入任何常规池，并使用 `noeden nochallenge nodaily nogreed` 标签，避免进入正常随机、挑战、每日和贪婪模式生成路径。它们不作为正常收藏进度目标。

拾取横幅副标题固定为：

| 道具 | 中文 | 英文 |
| --- | --- | --- |
| 小皮鞋 | 咪mermermer | Meowmermermer |
| 流量：开箱 | 初露锋芒 | A promising debut |
| 流量：曝光 | 更多人看见了你 | More eyes are on you |

英文 XML 是默认注册和 ID 查询来源；中文 XML 覆盖中文显示。EID 只做存在性检测后的可选注册，核心机制不依赖 EID。

## 2. 楼层启用与状态所有权

流量系统采用“楼层锁定”而不是实时持有判定：

1. 每次进入新层时检查一次所有玩家中是否至少一人持有小皮鞋。
2. 若层开始时持有，本层流量统计、HUD、敌人链登记和 Boss 流量结算全部启用。
3. 若层开始时未持有，本层完全不启用；中途获得小皮鞋也要等到下一层才生效。
4. 若已启用的本层中途失去最后一双小皮鞋，仅关闭后续敌人返回：
   - 尚未生成的返回体取消；
   - 已存在的返回体不被删除，仍按正常敌人处理；
   - 已登记的敌人链、房间死亡次数与本层累计流量不清空；
   - 后续合格敌人仍参与流量统计，但不再触发返回；
   - HUD 和 Boss 流量奖励继续正常工作。
5. 新层开始时始终清空上一层的房间状态与累计流量，再根据新层持有情况重新决定是否启用。

多人模式下楼层启用是全局开关，但角色状态、热度层数和属性缓存按玩家独立保存。多名持有者不会叠乘敌人返回概率，也不会为同一敌人建立多条链。

## 3. 合格敌人与动态分裂排除

### 3.1 合格敌人

本层启用时，所有处于敌对、可受伤且存活状态的普通 NPC 均可建立独立敌人链，包括：

- 房间初始普通敌人；
- 波次房后续生成的普通敌人；
- 敌人、Boss 或其他实体在存活期间正常召唤出的普通敌人。

不得因为 `SpawnerEntity` 存在就排除普通召唤怪。

### 3.2 固定排除

以下实体不建立链、不返回、不贡献流量：

- `IsBoss()` 为真或具有有效原版 Boss ID 的 Boss、小 Boss；
- 具有有效 Parent、Child、ParentNPC、ChildNPC 或有效分组索引的多节/分段实体；
- 由一次死亡直接产生的分裂子体，以及触发该次分裂的母体。

### 3.3 动态分裂识别

不维护按名称或未知模组内容猜测的全局分裂怪名单。死亡时先为候选实体创建短期判定记录，不立即结算返回；随后约两帧内观察新 NPC：

- 新 NPC 的 `SpawnerEntity` 指向刚死亡实体时，认定为死亡分裂子体；
- 将母体和这些子体全部标记为分裂链排除对象；
- 母体存活期间生成的普通召唤物不属于死亡分裂，因此仍可建立自己的链。

该策略同时保留召唤物兼容性，并避免把未知分裂怪错误地当作可返回敌人。

## 4. 敌人返回链

每个合格普通敌人拥有独立链 ID 和死亡序号。首次正常死亡计为第 1 次死亡：

| 当前死亡次数 | 返回概率 |
| --- | --- |
| 1 | 33% |
| 2 | 22% |
| 3 | 11% |
| 4 | 0% |

因此一条链最多死亡四次、最多返回三次。判定使用由房间种子、原实体 `InitSeed`、链 ID 和死亡序号共同派生的确定性 RNG；每次死亡只判定一次，不使用每帧随机。

死亡回调只保存快照和排队，返回体在后续更新中生成，避免死亡回调重入和房间提前清空。快照至少包含：

- Type、Variant、SubType；
- Champion 状态；
- 原死亡位置；
- MaxHitPoints；
- 链 ID 与下一次死亡序号。

返回体按原 Type/Variant/SubType 生成，恢复 Champion 后再把生命设为完整 MaxHitPoints，并继续使用对应原版 NPC 的正常 AI 和死亡掉落。模组不额外注入掉落。

## 5. 房间流量与清房时序

房间状态以“楼层种子/层、维度、房间索引”组成稳定键，记录：

- 本房所有有效链及各自总死亡次数；
- 待确认分裂记录；
- 待生成返回体；
- 是否已经结算流量；
- 是否已经完成 Boss 流量奖励。

当房间没有存活敌人、没有待确认分裂、没有待生成返回体，并且波次房已经结束时，结算：

`roomTraffic = max(本房所有有效敌人链的总死亡次数)`

例如三条链死亡次数为 5、6、2，房间流量为 6。没有有效链的房间为 0。每个房间只结算一次，重进、暂停、传送、门状态变化或重新加载房间均不得重复增加。

若原版准备生成清房奖励时仍有待确认或待返回实体，清房奖励被临时延后；机制完成后调用一次原版清房奖励路径。原奖励不替换、不复制。Boss 特殊出口和特殊房间清房流程必须在实机验证，静态测试只证明延迟状态机和单次释放契约。

## 6. 流量等级、HUD 与 Boss 结算

本层累计流量等级为：

| 流量 | 等级 | Boss 流量奖励 |
| --- | --- | --- |
| 0–5 | 无 | 无 |
| 6–7 | 1 | 流量：开箱 |
| 8–11 | 2 | 流量：曝光 |
| 12 及以上 | 3 | 流量：曝光 + 流量：热度，二选一 |

HUD 采用低侵入显示，仅在本层流量系统启用时绘制：

- 当前流量数值；
- 距下一等级还差的点数；
- 与等级对应的 1/2/3 级小标记；
- 达到 12 点后显示最高等级，不显示不存在的下一档门槛。

Boss 房真正清空、原 Boss 奖励应出现时，先把该房间流量计入本层总量，再按最终最高等级只生成一次流量奖励。原版 Boss 奖励完整保留。流量奖励在后续更新帧生成，随后本层累计流量清零；同一 Boss 房不能重复结算。

## 7. 三种流量衍生道具

### 7.1 流量：开箱

拾取确认后，道具底座消失并播放资源中的 `Pickup` 动画。到指定动画帧或动画结束时，在原拾取位置生成一个普通宝箱。每个真实拾取事件只生成一次。

### 7.2 流量：曝光

拾取确认时才读取当前房间的原版对应道具池，不在奖励生成时记录、预览或提前抽取。使用当前房间类型和房间种子取得池，再由该池抽取一个正常可拾取道具底座；Boss 房通常因此使用 Boss 池。无法可靠取得池时保留原流量底座并放弃本次转换，不静默改用全局池。

### 7.3 流量：热度

每次真实拾取使该玩家的永久热度层数增加 1。每层提供真实 `+0.5` 射速，使用射速与 FireDelay 转换：

1. `currentTears = 30 / (MaxFireDelay + 1)`；
2. `targetTears = currentTears + 0.5 * heatCount`；
3. `MaxFireDelay = 30 / targetTears - 1`。

缓存回调只根据已保存层数重算，不在缓存回调里增加层数，因此反复 `EvaluateItems()` 幂等。不同玩家分别计算；多次独立获得热度可以叠加。

### 7.4 三级互斥选择

等级 3 的曝光和热度共享唯一 choiceGroup。任意玩家确认碰撞其中一个时，先原子化锁定选择，再立刻移除同组另一个底座和 `traffic_choice_link` 特效，最后执行所选道具效果。碰撞回调正常路径返回 `nil`，不得取消原拾取；合作模式下同一组只能成功一次。

## 9. 回调职责与返回契约

| 回调 | 职责 |
| --- | --- |
| `MC_POST_GAME_STARTED` | 初始化运行状态、恢复永久热度层数 |
| `MC_POST_NEW_LEVEL` | 清空旧层流量并一次性锁定本层是否启用 |
| `MC_POST_NEW_ROOM` | 绑定稳定房间状态，执行必要的一次性初始敌人登记 |
| `MC_POST_NPC_INIT` | 登记后续波次/召唤普通敌人，识别死亡分裂子体 |
| `MC_POST_ENTITY_KILL` | 记录死亡、创建分裂观察和返回候选；正常返回 `nil` |
| `MC_POST_UPDATE` | 解析短期分裂观察、延迟生成返回体、释放清房、延迟生成流量奖励和衍生结果 |
| `MC_PRE_SPAWN_CLEAN_AWARD` | 仅在仍有待判定/待返回实体时返回 `true` 延迟奖励；其他路径返回 `nil` |
| `MC_POST_PICKUP_INIT` | 为三个隐藏流量底座加载对应 `Idle` 外观 |
| `MC_PRE_PICKUP_COLLISION` | 确认衍生道具拾取和三级互斥；所有正常路径返回 `nil` |
| `MC_EVALUATE_CACHE` | 幂等应用该玩家热度层数对应的真实射速 |
| `MC_POST_RENDER` | 绘制流量 HUD、拾取动画和 choice link |

实现放入 `main.lua` 独立 `do ... end` 作用域，避免继续占用顶层局部变量额度；不重构现有无关系统，不调用未在项目中确认存在的 helper。

## 10. 保存、错误处理与兼容边界

永久热度层数并入项目现有保存数据与保存函数，不创建名字相近但不存在的新 helper。临时敌人链、房间状态、待生成实体、choiceGroup 和 HUD 状态不持久化到跨局存档；继续游戏时以当前层/当前房间安全重建，不能重复发放已经确认的拾取效果。

所有外部兼容入口均为可选：EID 不存在时不报错；未知模组房间池不猜测；未知模组 NPC 仅按运行时实体关系判断 Boss、分段和死亡分裂，不扫描其他模组源码或描述文本。

## 11. 静态测试与实机验收

新增最小行为测试，至少证明：

1. 返回概率序列严格为 33% → 22% → 11%，最多返回三次、死亡四次；
2. Boss、小 Boss、分段实体、死亡分裂母体与子体不进入链；
3. 波次房普通怪、存活期间召唤出的普通怪进入独立链；
4. 4/3/2 的房间流量恰为 2，房间重进不重复结算；
5. 5 点不生成奖励；6、7 点仅开箱；8、11 点仅曝光；12 及以上仅曝光与热度互斥二选一；
6. Boss 结算后本层流量清零；
7. 曝光严格使用拾取时所在房间池；
8. 三级任一底座被拾取后另一底座和 link 立即消失，合作模式不能双拿；
9. 热度每层真实永久增加 0.5 射速，反复缓存不重复叠加，多玩家独立；
10. 层开始持有才启用；中途获得要等下一层；中途失去只停止返回、取消待生成返回体，流量统计、HUD 和 Boss 结算继续；
11. 普通碰撞/死亡/清房回调的 `nil`/`true` 返回契约正确；
12. XML 的 ID、品质、隐藏状态、池权重、本地化、EID 可选注册及资源路径一致。

静态验证完成后仍需实机确认：特殊 Boss 出口不会被延迟清房破坏、Champion 返回体外观与生命正确、分裂观察窗口覆盖原版分裂时序、波次房结束判断、HUD 位置、三个 Pickup 动画时机、曝光的各原版房间池、三级合作模式竞态、继续游戏后的热度保存，以及小皮鞋 My Stuff 占位帧显示。
