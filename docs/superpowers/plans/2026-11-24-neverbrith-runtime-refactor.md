# Neverbirth 整体重构计划

本次重构覆盖整个 Mod 的源码组织、引擎装配、共享机制、状态与存档、资源契约、测试和交付。完成后，维护者可以按职责找到代码，沿加载关系定位依赖，并以可回退的小批次迁移现有实现。

## 当前架构问题

| 问题 | 重构目标 |
| --- | --- |
| `main.lua` 有 20,882 行，集中了前置检查、兼容接入、状态管理、回调注册和大量玩法。 | 根入口只调用启动模块。启动、装配、共享服务和玩法有各自的维护位置。 |
| 有的玩法内联在入口，有的散在根目录，相关配置、输入、战斗和表现可能分开。 | 按内容身份和机制归位全部玩法实现。已有模块与新拆模块使用同一目录规则。 |
| 共享函数和状态经局部闭包、全局 Mod 对象与宽泛的上下文表流转。 | 为每个跨模块依赖确定提供方、消费者、接口和生命周期。 |
| 现有存档由入口里以八音盒命名的函数统一读写，许多内容共享可变根表。 | 明确总存档和每段数据的归属，继续读取原有存档格式。 |
| 测试、实机探针及部分工具依赖 `main.lua` 的源码文本、代码块标记或局部变量。 | 让测试从真实启动和模块接口进入。开发工具和安装产物一起验证目录迁移。 |

现状从当前源码、项目地图、检查说明和兼容指南核对。[项目地图](../../agent/project-map.md) · [检查与证据](../../agent/testing.md) · [中文兼容指南](../../../COMPATIBILITY.zh-CN.md)

## 最终目录结构

```text
neverbrith/
├── main.lua                 Isaac 的 Lua 启动入口
├── metadata.xml             Mod 元数据
├── runtime/                 引擎接入和全模组共用基础服务
│   ├── bootstrap.lua        REPENTOGON 版本门、唯一 Mod 实例、启动主链
│   ├── dependency_guard.lua 前置缺失时的提示和现有掉落保护
│   ├── content.lua          按确定次序装配服务、共享系统与玩法
│   ├── ids.lua              运行时 ID 查询和名称候选
│   ├── world.lua            当前玩家、房间和局种子等查询
│   ├── save.lua             JSON 读写、旧字段兼容和分区访问
│   ├── localization.lua    语言、字体和共用文案查找
│   ├── pickup_banner.lua   共用拾取提示跟踪与显示
│   └── eid.lua              EID 能力检查、注册与迟到接入
├── items/                   所有道具源码及道具专用配套
│   ├── 单文件道具.lua
│   ├── 多文件道具或系列/    同组的配置、输入、战斗、状态、表现和文案
│   └── trinkets/            饰品实现
├── systems/                 多组玩法实际共用的规则或状态
│   ├── inventory/           物品来源、临时物品、玩家库存键和选择界面
│   └── damage_payment.lua   已有的跨组伤害标记和付费伤害判断
├── characters/              角色实现，保持现有启用状态
├── generated/               全模组级生成登记与数据表
├── content/                 Isaac 的 XML 注册和内容入口
├── resources/               引擎加载的图像、动画和音频
├── tests/                   模块、完整启动、联动、资源和实机检查
├── tools/                   生成、静态检查、隔离验证和交付检查
└── docs/                    架构索引、兼容契约和维护说明
```

根目录已独立的道具和道具系列全部纳入 `items/`。道具专用配套随所属内容归位。跨内容的物品来源、库存和选择逻辑归同一系统，公共基础服务归 `runtime/`。引擎直接解析的路径按现有契约维护。逐项归位清单在实施时从真实加载图生成，包括源路径、目标路径、消费者和检查入口。

## 架构契约

### 入口与回调

最终根 `main.lua` 只有 `include("runtime.bootstrap")()`。启动层负责前置判断。支持分支创建并公布原来的 Mod 对象，再调用 `runtime/content.lua`。诊断分支仅加载现有提示和掉落保护。装配层按原生执行约束创建服务和系统，并用直接字面量 `include` 接入内容。

回调由拥有该行为的模块登记。跨模块的初始化时机由装配层决定。迁移前后对照回调 ID、优先级、过滤项、同优先级顺序、返回和短路行为。外部 EID 等注册以真实服务可用性和当前 Mod 实例为准，沿用现有早到、迟到和缺失分支。重载时核对外部持有的引用及需要主动清理的回调。

### 内容与依赖

- `runtime/content.lua` 只装配。顺着它能查到模块的实际加载位置、传入的服务和直接联动关系。
- 道具实现从 `items/` 查找。多文件道具按功能身份归组，专用的数值、状态、表现和回调由组内维护。角色、原生资源和共享系统分别有明确入口。
- `systems/` 里的代码要有真实的跨内容消费者，或承担多个内容共同依赖的状态。规则提供方导出窄接口，消费者接收同一个实例所需的方法。公共世界查询和基础设施留在 `runtime/`。
- 依赖沿装配层指向内容和提供方。内容通过参数或已有接口访问所需能力，提供方拿到的依赖同样可追踪。公开兼容接口仍由原来的 `Neverbirth` 对象提供。

### 状态与持久化

| 状态 | 所有者 | 何时建立或回收 |
| --- | --- | --- |
| 入口装配、ID 和服务实例 | 启动与装配层 | 随游戏实际加载和重载建立。 |
| 运行期数据、计时器、实体引用、输入和显示 | 对应玩法或共享系统 | 由原有玩家、房间、楼层、游戏局和卸载事件处理。 |
| 持久化 JSON 根及旧字段补全 | 存档服务 | 保留惰性读取与既有落盘时点。 |
| 某段持久化数据的字段、玩家键和复位策略 | 该玩法或系统 | 按原有继续、新开局、退出和沙漏行为处理。 |

迁移时先把原读写原样收进一个实例。随后按旧 JSON 顶层键给每个调用者提供自己的访问入口，覆盖读取、替换、清除和原时点保存。共享字段有一个写入方和明确的读接口。旧键、未知字段、运行局判断和已支持的恢复路径都纳入回归。原档与测试档分开，测试结果包括旧档加载与迁移前版本读取测试档。

## 实施顺序与验收

| 阶段 | 交付 | 通过标准 |
| --- | --- | --- |
| **0. 建立基线** | 从当前工作区建立隔离副本。登记实际加载图、回调持有者及顺序、公开 API、存档字段、XML／生成登记／资源引用，并列出所有依赖源文件路径的工具及测试。 | 现有检查能重跑，有结果和警告明细。新增完整入口测试覆盖正常、前置缺失、前置不兼容和相应诊断路径，记录真实加载关系。 |
| **1. 拆启动边界** | 抽出版本门、Mod 实例注册和诊断。过渡阶段由原入口接收启动结果，后续代码继续从现有位置执行。 | 正常分支实例唯一，缺失前置时仅装配保护。实际启动路径、公布的 Mod 对象和支持版本规则与基线一致。 |
| **2. 拆基础服务** | 把运行时 ID、世界查询、语言、拾取提示和 EID 归位。记录各接口何时可用以及文案、登记、回调之间的依赖。 | 比对运行时 ID、语言选择、登记数据、资源引用和外部 EID 加载顺序。模块只接收所需服务。 |
| **3. 拆状态与存档** | 收口 JSON 读写，再逐组建立持久化分区接口。运行状态仍随所属机制的事件更新和清理。 | 存档语义往返一致。多模块交错写入、旧字段、未知字段、不同玩家、不同局及继续游戏均有对应验证。隔离档实机验证适用的退出和沙漏路径。 |
| **4. 归位全部玩法与共享系统** | 迁出所有内联机制，并归位根目录已独立模块。逐组更新加载、生成、测试和文档路径。独立处理已确认的跨内容共享依赖。 | 每组迁移都有局部回归和完整入口验证。最终全部道具归 `items/`，共享系统有明确的提供方，根目录旧实现和重复装配已撤除。 |
| **5. 收口装配并切换薄入口** | 把剩余装配顺序收进 `runtime/content.lua`。根入口改成单行调用。补齐对新目录的递归语法检查、真实加载图检查和路径相关探针。 | 对照完整回调顺序，保留兼容 API。验证冷启动、游戏支持的重载、启用与停用分支。当所需模块缺失时，检查能定位文件。 |
| **6. 验证完整安装产物** | 在隔离交付目录检查启动、全部运行模块、生成表、XML、资源和对应探针。验证入口恢复与批次回退。 | 将隔离副本的入口移开，再只补回同版本入口即可完成启动。整包通过静态检查、行为回归和实机验收矩阵。每批的回退文件及实际结果可追溯。 |

每批先确认能证明原行为的测试，再迁移正式实现并核对结果。同一批带上其必要的测试、路径引用、生成器和交付配置。各批以当前玩法、数值、道具池、资源路径、Mod 身份及 REPENTOGON 支持条件为验收基线。遇到行为与既有设计不一致，单独记录证据与影响，由玩法修改处理。回退以隔离副本中上一批通过检查的版本为准，避免覆盖原工作区和玩家档案。

## 整体验收矩阵

| 层面 | 必须验证 |
| --- | --- |
| 启动与加载 | 完整入口、缺失模块和嵌套语法错误、正常前置与诊断分支、冷启动和重载、只有一次预期注册。 |
| 玩法和联动 | 模块自治、联动调用、回调优先级和短路、触发时序、RNG 与性能敏感路径的既有行为。 |
| 状态和存档 | 旧档继续、多人状态隔离、新开局、退出、换房／换层、按原行为支持的沙漏和回退读档。 |
| 原生登记和显示 | XML 本地 ID 与运行时 ID、生成表、双语注册、资源引用、EID 缺失和迟到、原生显示入口。 |
| 兼容与交付 | 外部 Mod API、实际安装目录、入口和必需文件缺失诊断、单独补回入口、整批回退。 |

现有总回归入口用 `pwsh -NoProfile -File tools/check-neverbrith.ps1 -Profile LuaAll`。按变更范围补跑检查入口自测、严格验证器范围测试、完整兼容示例、资源专项与实机测试。每项记录命令、退出码、警告及覆盖边界。静态、模拟与原生结果各自有来源。[检查说明](../../agent/testing.md)
