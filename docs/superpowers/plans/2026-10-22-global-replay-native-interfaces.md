# 全局回放原生接口实施与分批验证计划（Implementation Plan）

> **For agentic workers**：后续获得实施授权后，使用 `superpowers:executing-plans` 按批执行；用户若明确选择并行实施，再使用 `superpowers:subagent-driven-development`。本轮只写文档，以下勾选项全部未执行，不表示已授权实施。

**目标**：优先证明战斗现场完整恢复，最终同时满足整局回放、跨重启保存与分享、接管练习不影响正式进度、结束后精确返回发起时原房间状态。

**架构**：原生层拥有检查点、实体图、输入/时钟/RNG、持久化隔离及状态验证；Lua 层通过专用参与者协议管理 Mod 状态和会话。A 为冻结的正式局返回点，B 为不可变回放目标，C 为可丢弃练习分支；完整性和隔离门槛在玩家入口之前。

**技术**：本机 Isaac Repentance x86、匹配的 REPENTOGON 隔离源树及原生工具链、当前项目 Lua 运行时。新增序列化与状态协议均需验证，不预设新上游 ABI 可用。

**设计依据**：[八组原生接口详细设计](../specs/2026-10-22-global-replay-native-interfaces-design.md)。记录日期：2026-10-22；计划和所有用例状态为 `NOT_STARTED`。

## 1. 全局约束

- 最终范围是完整一局；不能用“只支持单房”“只存种子”“回房间入口”替代最终目标。
- 回放保存到磁盘，退出游戏、重启后仍能播放；支持环境中的接收方可以验证分享包后播放。
- 观看、跳转、练习及其失败都不改变正式局进度、正式 Continue、成就、解锁或其他持久化数据。
- 正常结束练习返回 A：原房间、原位置、原战斗帧和原正式局状态；不能只传送回同一个房间编号。
- 不改 neverbrith 已确认玩法及沙漏语义；回放拥有独立协议。
- 当前工作区和原生研究树有无关修改。实施时建立独立原生源树，按最小文件范围修改；无提交、推送、发布或覆盖正式 DLL 的默认授权。
- 批次通过以真实证据为准。源码存在、文档检查、模拟器、编译、安装、原生调用成功、真人玩法验收分别记录。
- 不在正式进度上做原生恢复试验。B00 必须先证明独立测试资料和受保护路径边界；B07 与最终门槛通过前不开放正式局入口。
- 所有接口 ID 和类型沿用设计文档。它们是拟议 API，字段/ABI 尚未闭合项标记为 `Unverified — discovery required`，不能伪装为已存在。

## 4. 共用验收方法

### 4.1 每个批次的证据包

存放 `reports/replay/<日期>/<批次>/`，至少包含：实际 EXE/DLL/Mod/资源哈希和加载顺序、原生接口能力报告、fixture 身份与生成步骤、字段覆盖表、逻辑输入与时间线、随机审计、逐域/逐帧摘要、首个差异、受保护文件/内存前后比较、异常注入点、操作日志和人工画面观察。没有运行的用例保持 NOT_STARTED。

实施后状态只使用 `NOT_STARTED`、`RUNNING`、`PASS`、`FAIL`、`BLOCKED`；BLOCKED 必须写具体外部依赖，不以它代替失败。本文初始 88 项用例均为 NOT_STARTED；本文档检查只能检查结构与链接，不能把这些状态改成 PASS。

### 4.2 完整恢复的三层比较

1. **静态当前帧**：捕获后原世界与恢复世界的分域规范状态相等，身份图、输入前态、所有计时/RNG/队列相等。不要比较原生地址、padding 或真实日志时间。
2. **分叉续跑**：一支保留捕获现场的真实原世界直接续跑并记录基准，另一支从检查点恢复后重演；输入、时间推进和环境相同，逐逻辑 tick 比较状态、引擎事件与随机审计。另做两次恢复互比，但不能只用两个都经过同一有缺陷 Restore 的分支互证。基础 fixture 至少 300 tick；跨结算/长延迟 fixture 至少 1,200 tick，或运行至其全部相关事件结束，取较长者。
3. **返回完整性**：在 C 中主动改变状态，回到 A 后先比较当前帧，再与从未进入练习的 A 控制分支用相同输入续跑至少 300 tick。正式存储、内存读视图和外部提交还要独立比较。

每个正向恢复 fixture 连续进行 32 次 Capture/Clone/Restore/Release；验证逻辑完全一致、引用不串代、资源计数无单调增长。32 次是初始验收下限，不代表排除更长时间问题。涉及概率的 fixture 至少 4 个固定种子；复杂 Boss/武器按 B00 覆盖清单增加组合，不能用种子数量代替类型覆盖。

### 4.3 引擎边界与性能

捕获点选“完整模拟 tick 结束、下一 tick 开始前”的已验证边界；事件队列可能非空，应保存而不是强制清空。用户在 tick 中途请求时排队到本 tick 完成后的边界，入口在该边界正式接受请求并冻结 A；不额外运行下一 tick 来等清场。过渡期间若请求不能在该边界接受，报告具体阶段并保持入口未进入；重新可用后再接受入口请求，不无声推进正式局并更换已接受的 A。发起帧指入口实际接受时的完整模拟帧，绝不改成进房点。

记录 Capture、Restore、Step、Export/Import 的耗时、峰值内存、包大小与队列规模。第一批测量后建立真实基线和资源上限，B11 根据相同 fixture 比较退化；不在没有机器实测前编造“必定一帧恢复”的性能承诺。超预算在破坏宿主前返回 RESOURCE_LIMIT；超过时延仍不得漏恢复字段。

### 4.4 各批通用执行步骤

- [ ] 核实依赖证据、工作区基线、受保护路径和本批接口/字段来源。
- [ ] 先建立本批表内的失败/缺字段/失效引用用例，确认能暴露当前缺口；运行器的断言失败与游戏进程崩溃分别记录。
- [ ] 只实施本批接口和字段；新增类型必须同时加入覆盖表、摘要和错误报告。
- [ ] 跑协议/原生检查，再在独立测试环境跑本批真实引擎用例；按需进行人工画面/手感检查。
- [ ] 记录精确命令、退出码、原生调用次数、首差和存储比较；通过后再按依赖矩阵开放下一批。
